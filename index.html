FinTechCo estate architecture

A stand-in payments estate — three languages, two clouds, four repositories — and the agentic coding setup built around it.

FinTechCo is fictional. This is a stand-in estate built to demonstrate how an agentic coding tool behaves across a realistic multi-language, multi-cloud codebase. Nothing here is a production system and no real customer data exists in it. Cloud account identifiers, API hostnames and project names are redacted on this page and shown as «placeholder».

The estate on one screen

Where people work, where the model calls go, what gets deployed to which cloud, and what is read back. No repository names and no individual cloud resources — those are in the second diagram.

Three surfaces, one tool, one model plane. Writes to the clouds are builds and deploys and go through checked-in scripts; reads are logs, metrics and deploy state — the read-only surface an SRE investigates with. Policy sits above all of it, in the repository, reviewed like any other change.

This is the reference shape, not a photo of one machine. The model plane is Claude on Amazon Bedrock — inference inside your own AWS account, so the controls you already operate apply to the call itself: an SSO login rather than a distributed API key, IAM for access, CloudTrail for the record, VPC endpoints for the path, Guardrails where you want them. Billing is ordinary AWS service billing on the agreement you already signed, not Marketplace, and it lands in Cost Explorer beside everything else. Data retention is an explicit setting — none means no request or response data written to durable storage or shared with the model provider — set per region and per control plane, provable by API, and lockable org-wide with an SCP. The second half of the plane is the Claude apps gateway, self-hosted between the clients and Bedrock: developers hold an identity-provider session instead of cloud credentials, and model access and managed-settings policy are enforced server-side per IdP group rather than by a file on the device. Device management does not disappear behind it — it shrinks to a bootstrap, because the CLI has to learn where the gateway is before the gateway can tell it anything — and policy from the repository, the device and the identity provider are three separate sources that must not be split across. The detailed diagram below is the estate as actually built: its desktop sessions authenticate to the Anthropic API with a personal credential rather than through an enterprise AWS account, and the notebook surface is specified but not yet stood up. Worth stating precisely either way — SageMaker runs the client, not the model. Claude's weights are not deployed to a SageMaker endpoint, and no inference happens inside the notebook.

What you are looking at

One payments platform, split across four separately managed repositories and two cloud providers. The diagram shows both halves of the picture at once: the running systems, and the development setup that builds and deploys them.

FlowPay · Python

The payments API — charges, refunds, idempotency — plus a double-entry ledger. Runs on AWS as API Gateway → Lambda → DynamoDB, with no container anywhere in the build.

Merchant dashboard · TypeScript

The merchant-facing web app. Runs on GCP Cloud Run, where nginx serves the built site and reverse-proxies the API path back to AWS — so the browser stays same-origin and the API needs no CORS.

Settlements · Java 21

An observer service: it reads charges the payments API has already committed, derives a settlement position per charge, and writes a daily file. It cannot write back — that constraint is enforced by its IAM policy, not by convention.

Analysis workspace · Python

A notebook workspace for economic data analysis. Local today; the diagram shows where it goes next — a managed notebook environment, with the agent running in the terminal beside the data.

Four surfaces, deliberately scoped

The interesting part of the diagram is not the clouds — it is the sessions, and what each one is allowed to touch. Claude Code is a command-line tool with editor integrations, so the surface is wherever a given group already works. Two of these run in this estate today; the other two are the same tool, pointed at a different seat.

SessionScopeBuilds and deploys
VS Code, opened at the estate root Python, TypeScript, and the architecture record — everything except the Java service The payments API to AWS, and the dashboard to GCP, through checked-in deploy scripts
IntelliJ IDEA, opened at the settlement service That one repository only. It cannot open the Python it reads from The settlement service to AWS, once its deploy script is verified
SageMaker Studio — data scientists A notebook workspace beside the data. The managed JupyterLab environment is ordinary Linux with a terminal, so the CLI installs and runs there like anywhere else — and where the agent is wanted inside the notebook, the Agent SDK (pip install claude-agent-sdk) gives the same agent loop as a library in your own process Nothing. Analysis work produces findings and charts, not deployments — and it publishes its own readout when asked
Any terminal — SREs Read-first. describe, get and list are allowlisted, so chasing an incident is not interrupted every thirty seconds to approve a read — and anything that would change infrastructure stops and waits for a human. In this estate those changes are denied outright rather than gated, because a demo has no reason to make them; a real deployment moves them from deny to ask, which is a settings change Nothing without approval. It reads logs, metrics and deploy state to answer “what changed, and when?”, and a person authorises anything that follows

The narrow scope is the design, not a limitation. The settlement service is an observer; a session that cannot open the payments service cannot accidentally “fix” it while working on settlement. The wider session gets the opposite treatment, because an impact analysis that cannot read the dashboard is not an impact analysis.

The bottom two rows matter for a different reason: they are not separate products. The data scientist in a notebook and the SRE in a terminal get the same binary, the same permission model and the same policy files as the engineers — pointed at a different seat and scoped to different work. The SRE surface is the clearest case: its entire capability is the read-only cloud allowlist this estate already uses for its own audits, which is why an investigation session cannot turn into a change.

Skills and MCP servers — two different mechanisms

Both diagrams show the tools a session reaches beyond the codebase, and it is worth being precise about which mechanism does what, because they get conflated.

MechanismWhat it isHere
MCP server A live connection to another system, exposing its operations as tools the agent can call The IDE, exposing diagnostics and the open file so a session sees what the editor sees rather than a parallel view rebuilt from grep. Slack, for posting a finished readout to a channel
Plain CLI A command-line tool the agent already knows how to drive, subject to the same permission rules as any other command gh, for pull requests and repository state. No integration was needed — it is the tool the engineers already use, and the permission layer already covers it
Skill A written procedure the session follows — the steps, the checks, and what not to do. It can drive anything underneath, including a plain REST API Mirroring the delivery record onto the Jira board: dry run, show the diff, get approval, then apply. No MCP involved — the hard part is the procedure, not the transport

Prefer the plain CLI when one exists. Pull requests are the clearest case: /commit-push-pr is a skill that drives gh, and GitHub Actions then runs the test suite on the result exactly as it would for any engineer. Nothing in the review path is special-cased for an agent — no new approval mechanism had to be invented, because the existing one already works.

The rule of thumb: reach for MCP when you need a live connection to a system, and a skill when the hard part is the procedure rather than the transport. The Jira sync is the clearest case — writing issues is a single API call, but doing it safely means never applying before a human has read the dry run, and never inventing a work item the repository cannot evidence. That is a procedure, and it belongs in a file that travels with the repository.

Where the Agent SDK fits

A managed notebook space is ordinary Linux with a terminal, so the CLI installs and runs there directly — nothing has to be built to put an agent in front of a data scientist. The Claude Agent SDK is the answer to a different question: what if we want the agent inside our own software? It is the same agent loop, tools and context management that power the CLI, available as a library in Python and TypeScript and running in your process.

WhereWhich oneWhy
In a notebook cell Agent SDK The agent and the analysis end up in one artifact, reviewable and re-runnable together, instead of a chart whose provenance lives in a terminal someone has closed
In CI, or any pipeline Agent SDK, or the CLI headless Unattended work — a migration across hundreds of files, a standards check on every pull request. The CLI runs headless with -p --output-format json when the surrounding code is not Python or TypeScript
Inside an internal tool Agent SDK An incident triage service, a compliance reviewer, a support-facing assistant — anything where the interface is your product rather than a terminal
At a developer's desk The CLI Interactive work. Building a harness to wrap it adds a layer without adding a capability

The governance story does not fork. The SDK loads the same .claude/ skills, commands, memory and permission rules as the CLI, so a policy written once for the repository applies to an engineer's session, a notebook cell and a pipeline job alike. The agent loop is where permission decisions get made — tool allow and deny, approval prompts, hooks, file scoping — so adopting the SDK means inheriting that layer rather than building it.

This is not a security argument about the API. The model, the endpoint, the safety behavior and the enterprise controls are identical whichever route you take — on Bedrock, IAM access control, VPC endpoints, CloudTrail and Guardrails apply to the call regardless of what made it, and behind a self-hosted gateway so does the server-side model and policy enforcement. The difference sits one layer up: whether the loop between the model and your filesystem is one you wrote or one you adopted. Building your own is a legitimate choice, and a purpose-built harness with no shell tool at all is more restrictive than a general-purpose one. The question is not which is safer, but whether that layer is something you want to own and maintain.

What the agent may do to a cloud

Read-only calls — describe, get, list — are allowlisted. Calls that create, update or delete cloud resources are denied outright. Deploys therefore run through the same idempotent scripts a person would run, which means the audit workflow can read live cloud state and compare it against the documentation without being able to change either.

The one house rule

Money is integer cents at rest and on the wire — parsed and formatted only at the edges. It holds in all three languages, which is what makes a cross-language change reviewable: the same rule, stated once, checked in Python, TypeScript and Java.
