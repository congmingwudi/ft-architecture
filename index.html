FinTechCo estate architecture

A stand-in payments estate — three languages, two clouds, four repositories — and the agentic coding setup built around it.

FinTechCo is fictional. This is a stand-in estate built to demonstrate how an agentic coding tool behaves across a realistic multi-language, multi-cloud codebase. Nothing here is a production system and no real customer data exists in it. Cloud account identifiers, API hostnames and project names are redacted on this page and shown as «placeholder».

The estate on one screen

Where people work, where the model calls go, what gets deployed to which cloud, and what is read back. No repository names and no individual cloud resources — those are in the second diagram.

What you are looking at

One payments platform, split across four separately managed repositories and two cloud providers. The diagram shows both halves of the picture at once: the running systems, and the development setup that builds and deploys them.

FlowPay · Python

The payments API — charges, refunds, idempotency — plus a double-entry ledger. Runs on AWS as API Gateway → Lambda → DynamoDB, with no container anywhere in the build.

Merchant dashboard · TypeScript

The merchant-facing web app. Runs on GCP Cloud Run, where nginx serves the built site and reverse-proxies the API path back to AWS — so the browser stays same-origin and the API needs no CORS.

Settlements · Java 21

An observer service: it reads charges the payments API has already committed, derives a settlement position per charge, and writes a daily file. It cannot write back — that constraint is enforced by its IAM policy, not by convention.

Analysis workspace · Python

A notebook workspace for economic data analysis. Local today; the diagram shows where it goes next — a managed notebook environment, with the agent running in the terminal beside the data.

Four surfaces, deliberately scoped

The interesting part of the diagram is not the clouds — it is the sessions, and what each one is allowed to touch. Claude Code is a command-line tool with editor integrations, so the surface is wherever a given group already works. Two of these run in this estate today; the other two are the same tool, pointed at a different seat.

The narrow scope is the design, not a limitation. The settlement service is an observer; a session that cannot open the payments service cannot accidentally “fix” it while working on settlement. The wider session gets the opposite treatment, because an impact analysis that cannot read the dashboard is not an impact analysis.

The bottom two rows matter for a different reason: they are not separate products. The data scientist in a notebook and the SRE in a terminal get the same binary, the same permission model and the same policy files as the engineers — pointed at a different seat and scoped to different work. The SRE surface is the clearest case: its entire capability is the read-only cloud allowlist this estate already uses for its own audits, which is why an investigation session cannot turn into a change.

What the agent may do to a cloud

Read-only calls — describe, get, list — are allowlisted. Calls that create, update or delete cloud resources are denied outright. Deploys therefore run through the same idempotent scripts a person would run, which means the audit workflow can read live cloud state and compare it against the documentation without being able to change either.

The one house rule

Money is integer cents at rest and on the wire — parsed and formatted only at the edges. It holds in all three languages, which is what makes a cross-language change reviewable: the same rule, stated once, checked in Python, TypeScript and Java.
